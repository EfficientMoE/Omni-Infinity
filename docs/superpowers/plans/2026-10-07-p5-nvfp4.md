# P5 — NVFP4 weight path for the 33B H3 DiT (SM120)

> **Tracking PR** — implementation for this plan lands on this branch. Roadmap: #42.

Tracking: [#42](https://github.com/EfficientMoE/Omni-Infinity/issues/42) (P5).
Refs: [t2v survey](../../t2v_optimization_survey.md) §3B, reuse scan on #42.

## Objective

Exploit SM120's native FP4 tensor cores with a 4-bit weight path for the
33B DiT: halves weight bytes vs FP8 (bandwidth/offload-bound pipeline →
direct attack on the bottleneck). Accuracy-gated opt-in exactly like `fp8`
(`--fp4-scale …`), never the default. Depends on P1 landing the kernel
facade/build plumbing.

## Reuse-first strategy (before reaching for nunchaku)

In-house donors already exist:
- BatchGen `batchgen_kernels/src/moe/mega_moe_sm120.cu` — SM120 native FP4
  GEMM, per-32-element scales, 16×128 tile (+ py wrapper, build flags).
- BatchGen `batchgen/triton_kernels/fused_mxfp4_gemm.py` and MoE-Infinity
  `moe_infinity/kernel/mxfp4_gemm.py` — fused MXFP4 dequant+GEMM (E2M1,
  per-32 scales), pure Triton (universal wheel, slower).
- MoE-Infinity `marlin_gemm.py` — W4A16 Marlin fallback (fastest
  single-stream per SM120 ecosystem data).
- MoE-Infinity #221 phase-5 MXFP8 [1,32] E8M0 dequant — scale-format
  reference.
External (phase 3 only): SVDQuant/Nunchaku W4A4 with low-rank outlier
branch (RTX 5090-validated ~3×) via deepcompressor calibration.

## Approach (phased, each accuracy-gated)

1. **Phase 1 — W4 weight-only via Triton MXFP4** (dequant-in-kernel, bf16
   MMA): mirrors the existing FP8 weight-only design; quantizer in
   `kernels/_quant.py` gains an mxfp4 mode; store side adds an FP4 group
   format (moe-store converter flag). Expect memory win ≈2× vs FP8, latency
   ≈parity. QA: same golden harness as FP8 inc-8 (expect gate FAIL;
   record rms_rel; memory numbers are the deliverable).
2. **Phase 2 — native FP4 GEMM** for large Linears using the BatchGen SM120
   kernel (adapted from grouped-MoE to dense GEMM) or Marlin W4A16 as the
   pragmatic fast path; pick by microbench at H3 shapes.
3. **Phase 3 — SVDQuant-style outlier branch** if phase 1/2 rms_rel is far
   from the 2e-2 gate: low-rank BF16 side branch absorbs outliers
   (training-free calibration). Combine with P1's boundary protection
   (first/last blocks bf16).

## Verification

Same contract as FP8 inc-8: golden latents (256p/120f), explicit
pass/fail vs `rtol=2e-2`, memory deltas, s/NFE. Doc a quality ladder
(bf16 > fp8-block > fp4+outlier > fp4) in cache_benchmarks style.

## Risks

- H3 not FP8-native → FP4 accuracy likely worse; value is memory/bandwidth,
  not default quality. Keep messaging identical to the FP8 README stance.
- Dense-GEMM adaptation of the MoE kernel may be nontrivial → Marlin W4A16
  is the guaranteed-landable fallback.
- Store-format churn: version the group format; keep bf16 path untouched.
